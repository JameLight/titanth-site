# ร่างหน้าแจ้งเคส v4 — กู้เคสเมื่อคำตอบหลังส่งหาย

สถานะ: **candidate ปิดรับเคส**. ไฟล์ `intake-config.json` ยัง `enabled:false`, `schemaVersion:2`, URL/key ว่าง. ไม่ใช่หลักฐานว่ามี SQL รุ่นใหม่บนฐานจริงหรือมีทีมเฝ้าคิว และไม่ได้เปิดรับประชาชนจาก PR นี้

ต้นแบบหน้านี้เริ่มตรวจเทียบ SQL r10 ที่เก็บใน archive. ฉบับล่าสุดที่ตรวจอิสระ 27 ก.ย. คือ `sql_v26/supabase_setup_v26_candidate.sql` r13 SHA-256 `78dca85081bb86c3abf1148c5706611d206a672fe54db865c5d7bd108e727a51` คู่ SQL v2.7 SHA-256 `814913ccbd7908e2c23bb51a3e119dc258be6a174336c4dbd62f5fd09b55969b`. Codex ตรวจสิทธิ์สมาชิกใหม่และผู้ประสานที่ถูกถอนในฐานทิ้งด้วยข้อมูลสมมติแล้ว; Claude ทดสอบ HEAD `6bda684` กับ emulator และ Chrome จำลอง พบจุดแสดงผล 2 จุดที่แก้ใน source หลัง HEAD นั้น. ต้องทดสอบ HEAD ใหม่ตรงตัวอีกครั้ง. ผลทั้งหมดไม่ใช่ Supabase/PostgREST production หรือการมีทีมเฝ้าคิว

## สิ่งที่ผู้ใช้เห็น

1. กดบันทึกข้อมูลในเครื่องก่อนเหมือนเดิม ถ้าอันตราย โทร **1784** หรือ **1669** ตามเหตุ ไม่ต้องรอหน้าเว็บ
2. ถ้าระบบมีเวรและเจ้าของเปิดรับแล้ว จึงเห็นปุ่มส่งเข้าทีม กดแล้วอ่านประกาศและยินยอมแยก
3. ก่อนส่ง หน้าแสดง **รหัสกู้คืนส่วนตัว** ให้คัดลอกหรือจด แล้วกดยืนยันว่าเก็บไว้ รหัสนี้ใช้ดูสถานะหรือถอนข้อมูลละเอียดเมื่อคำตอบหาย อย่าส่งให้คนอื่น
4. หลังผู้ใช้ยืนยันเก็บรหัส หน้าใช้ธุรกรรม IndexedDB จองเคสพร้อมรหัสและข้อมูลเดิมทั้งชุด แล้วอ่านกลับก่อน POST. ถ้าเครื่องเก็บไม่ได้ หน้า **ไม่ส่ง** แม้ localStorage ใช้ได้ และชี้ให้โทร/ส่ง LINE ปภ. เอง วิธีนี้กันการส่งซ้ำจากสองแท็บที่สร้างรหัสต่างกัน
5. หากคำตอบหาย หน้าแสดง **อาจถึงระบบแล้ว** พร้อมปุ่ม **ดูรหัสกู้คืนที่เก็บในเครื่อง** และ **ตรวจอีกครั้งด้วยรหัสเดิม**. การตรวจซ้ำใช้ข้อมูลเดิมทั้งชุดกับรหัสเดิม ไม่สร้างรหัสใหม่ ก่อนลบข้อมูลในเครื่องต้องเก็บรหัสไว้ต่างหาก เพราะการลบในเครื่องไม่ถอนฐานข้อมูล ถ้าเครื่องลบข้อมูลแล้วแต่ยังมีรหัส ให้ใช้ช่อง **มีรหัสกู้คืนอย่างเดียว?** เพื่ออ่านสถานะหรือขอถอน
6. ถ้าระบบตอบว่ารับแล้ว หน้าแสดงสถานะที่ server คืนจริง เช่น “ระบบรับข้อมูลแล้ว ยังไม่มีทีมอาสากดรับเคส” หรือ “ทีมอาสาแจ้งว่ารับเคสแล้ว” การรับข้อมูลเข้าระบบไม่เท่ากับมีคนออกช่วย

## ขอบเขตและข้อกั้น

- รหัสสร้างด้วย `crypto.getRandomValues` 32 ไบต์เป็น hex 64 ตัว ก่อน POST ห้ามใช้เวลา/ข้อมูลเคส/`Math.random`
- IndexedDB เก็บรหัสและ payload แบบเต็มสำหรับ retry; ผู้ใช้เครื่องเดียวกันอาจเปิดดูได้ `localStorage` marker เก็บเพียง local case ID กับสถานะ `uncertain/confirmed/closed` ไม่มีรหัสลับหรือรายละเอียดเคส ข้อมูล export ตัดรหัสทั้งจาก receipt และ attempt. หาก IndexedDB เขียน/อ่านกลับไม่ได้ ระบบไม่ส่งเคสจากเว็บนี้
- บันทึกการส่งต่อจากรายการเดิมทำผ่านธุรกรรม IndexedDB กับแถวล่าสุด จึงไม่เขียนทับรหัสกู้คืน/ใบรับที่เพิ่งบันทึกจากอีกแท็บ; การลบเคสในเครื่องอ่านสถานะใหม่และตรวจว่าแถวยังเหมือนตอนยืนยัน หากเปลี่ยนจะไม่ลบ. ผู้ใช้ยังลบเคสที่มีรหัสได้เมื่อยืนยันเอง โดยต้องเก็บรหัสกู้คืนไว้ก่อน
- หลังระบบยืนยันถอนเคส หน้าเว็บจะลบสำเนาเฉพาะแถวในเครื่องที่ยังตรงกับรหัสเดิมและไม่เปลี่ยนจากอีกแท็บ หากเปลี่ยนจะไม่ลบและบอกให้ผู้ใช้ตรวจรายการล่าสุดก่อน
- หน้าเว็บไม่ใช้ `volunteers_joined` บอกว่ามีคนพร้อมช่วย เพราะค่านี้รวมคนสมัครที่ยังไม่อนุมัติ. การยอมรับส่งเคสต้องบอกว่าบัญชีทีมที่เจ้าของอนุมัติและอยู่เวรอาจเห็นรายละเอียดเมื่อรับเคส ทั้งนี้ต้องตรวจ RLS/สิทธิ์จริงของ SQL รุ่นสุดท้ายก่อนเปิดรับ
- ถ้า server ตอบ `SECRET_CLOSED` แปลว่ารหัสเดิมใช้กับเคสที่ถอน/ลบแล้ว **เคสใหม่นี้ไม่ได้ส่ง** หน้าเก็บสถานะปิดเฉพาะเคสเดิมและไม่แสดงปุ่มส่ง/ลองซ้ำกับเคสนี้ ผู้ใช้ต้องเริ่มเคสใหม่เองหลังอ่านเหตุผล
- ถ้าไม่มีรหัสกู้คืนหลังเครื่องล้างข้อมูล จะตรวจหรือถอนทางเว็บไม่ได้ ต้องมีช่องทางเจ้าของระบบและขั้นตอนตรวจสิทธิ์ที่พิสูจน์ได้ในประกาศจริง
- ประกาศความเป็นส่วนตัวที่ config จะชี้ไปยังไม่อธิบายรหัสกู้คืน/attempt และการเก็บในเครื่องครบ จึงยัง **HOLD** การเปิดรับคนจริง. การมี checkbox บนหน้าไม่ใช่หลักฐานว่า server เก็บ consent ครบทุกชนิดข้อมูล
- HTTP anti-frame header จริง, PostgREST/RLS/config readback, ทดสอบสองเครื่อง/เครือข่ายร่วม/มือถือเก่า/offline/ถอน/ล้าง storage/ทีมเฝ้าคิว และอนุมัติเผยแพร่เฉพาะขั้นยังไม่ครบ. Service worker candidate เปลี่ยนเป็น cache v33; ต้องทดสอบผู้ใช้ที่ถือแคชเดิมด้วย
