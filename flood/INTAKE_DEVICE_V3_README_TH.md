# ร่างหน้าแจ้งเคส v3 — รหัสสุ่มต่อเบราว์เซอร์

**สถานะ:** โค้ด candidate เท่านั้น. `intake-config.json` ในเว็บจริงยัง `enabled:false`, `schemaVersion:2`; ฐานจริงยังไม่มี SQL v2.6 และไม่มีทีมเฝ้า. ห้ามใช้ผลทดสอบนี้อ้างว่าเปิดรับเคสแล้ว.

## ทำไมต้องเปลี่ยน

SQL v2.6 r8 มี `p_device` สำหรับนับ 3 เคสต่อเบราว์เซอร์ใน 10 นาที และนับรวม 20 เคสต่อเครือข่าย. ถ้าหน้าเว็บไม่ส่ง `p_device` จะมีเพดานอีกชั้นที่ 3 เคสต่อเครือข่ายใน 10 นาที. หลายโทรศัพท์ที่ใช้ Wi-Fi ศูนย์พักพิงเดียวกันอาจถูกปฏิเสธเพราะถึงเพดานรวม 3. นี่เป็นการลดปัญหานั้น ไม่ใช่การพิสูจน์ว่าผู้แจ้งเป็นใครหรือกันการส่งเท็จได้หมด.

## ขอบเขตของโค้ดนี้

- เมื่อผู้ใช้กดส่งเคสและมีเวรที่ระบบตอบว่าพร้อม เบราว์เซอร์สร้างรหัสสุ่มด้วย `crypto.getRandomValues` แล้วเก็บใน `localStorage` เพื่อใช้รหัสเดิมในการส่งครั้งถัดไป. ไม่มีชื่อ เบอร์ พิกัด หรือข้อมูลเคสในรหัสนั้น. SQL ผสมรหัสกับค่า secret ก่อนเก็บตัวนับ. รหัสที่ยังอยู่ในเบราว์เซอร์เชื่อมการส่งจากเบราว์เซอร์นั้นได้ จึงต้องอธิบายตรง ๆ ในประกาศความเป็นส่วนตัว.
- ถ้าเครื่องไม่ให้ใช้ที่เก็บหรือการสุ่มที่ปลอดภัย จะไม่ส่ง `p_device`; SQL ใช้เพดานต่อเครือข่ายแบบไม่มีรหัสแทน. ข้อความผิดพลาดบนหน้าใช้คำกลางว่าเครื่องหรือเครือข่าย เพราะ client แยกเหตุของเพดานที่ server ปฏิเสธไม่ได้.
- หน้าใหม่รับเฉพาะ config `schemaVersion:3`; config ปิดเดิม `schemaVersion:2` จึงยังปิดหลัง merge. รุ่น config อย่างเดียวไม่ยืนยันว่าฐานอัปเกรดแล้ว: ก่อนส่งข้อมูลเคส client ต้องอ่าน `system_totals()` ของ v2.6 และเห็น `intake_open=true`, `duty_locked=false`; ถ้า RPC ไม่มี/อ่านไม่ได้/ยังปิด จะไม่ส่งข้อมูลและชี้ไป 1784/LINE ปภ. การเปิดปิดที่เปลี่ยนหลังตรวจยังถูก SQL ตรวจซ้ำตอน `submit_case()`.
- เมื่อ SQL v2.6 ตอบ `INTAKE_CLOSED` หน้าแจ้งให้โทร 1784/ส่ง LINE ปภ. เอง; ถ้า `case_status()` ระบุ `stale=true` สำหรับเคสที่ทีมเคยรับ/ขอข้อมูล/บอกว่ากำลังไป หน้าเตือนว่าไม่มีการอัปเดตและให้โทรตามเหตุ โดยไม่เปลี่ยนสถานะจริงของเคสแทนทีม. ทดสอบข้อความจากข้อมูลสมมติแล้ว ยังต้องทดสอบหน้าโทรศัพท์จริงก่อนเปิด.

## ลำดับที่ต้องตรวจและอนุมัติก่อนเปิดจริง

1. ติดตั้งและอ่านกลับ SQL v2.6 บนโปรเจกต์จริง พร้อมตรวจ RPC, RLS, สวิตช์ปิด, Cron และเพดานเครือข่ายด้วยข้อมูลสมมติ. ถ้า gateway ไม่ส่ง IP ตามที่ SQL คาด เพดานเครือข่ายอาจไม่ทำงาน.
2. ประกาศความเป็นส่วนตัวต้องอธิบายรหัสสุ่มในเบราว์เซอร์, ค่าแฮชบนฐาน, ระยะเก็บจริง และข้อจำกัดของการลบ; อ่านกลับหน้า HTTPS จริง.
3. ทดสอบโทรศัพท์จริงหลายเครื่องบนเครือข่ายเดียวกันโดยไม่ใช้เคสคนจริง แล้วจึงพิจารณา config `schemaVersion:3` กับสวิตช์ server. ต้องมีคนเฝ้าคิวตามช่วงที่แจ้งไว้ และเจ้าของต้องอนุมัติการเปิดข้อมูลผู้เดือดร้อนแยก.

**ยังไม่ทราบ:** ผล gateway IP, การเก็บ `localStorage` บนอุปกรณ์จริง, ผล Cron รอบจริง, และความสามารถของผู้รับเรื่อง. ผล Node mock พิสูจน์เพียง payload และการปิดเมื่อ contract ไม่ตรง.
